# Incident Response

> **예시 안내**: 심각도 임계값/지표 예시는 일반적인 백엔드 서비스 기준입니다.
> 실제 SLO·온콜 체계·연락 채널은 조직 상황에 맞게 교체하세요. 스택이 미정이면 [tech-stack 규칙](../../.claude/rules/tech-stack.md) 참고.

## 목적

서비스 장애(인시던트)를 **감지 → 완화 → 복구 → 공유**하는 표준 대응 절차와 역할,
심각도 등급(SEV1~3), 포스트모템 템플릿을 정의한다.

핵심 원칙: **사용자 영향 최소화(완화)가 원인 분석보다 우선**한다.
지표/알림은 [observability](../architecture/observability.md), 되돌리기는 [rollback-guide](./rollback-guide.md), 운영 작업은 [runbook](./runbook.md) 참고.

## 1. 심각도 등급 (Severity)

| 등급 | 정의 | 예시 | 대응 시간(예시) | 소집 |
| --- | --- | --- | --- | --- |
| **SEV1** | 전면 장애 / 핵심 기능 전체 불가 / 데이터 손상·유출 | 전체 서비스 다운, 로그인·결제 전면 실패, PII 유출 | 즉시(24/7) | IC + 관련 전원 |
| **SEV2** | 부분 장애 / 핵심 기능 저하 / 다수 사용자 영향 | 특정 API 에러율 급증, p99 지연 SLO 초과 지속 | 영업시간 + 온콜 | IC + 담당 |
| **SEV3** | 경미 / 우회 가능 / 소수 영향 | 비핵심 기능 오류, 간헐적 오류, 성능 약간 저하 | 영업시간 | 담당자 |

등급 산정 가이드:

- 애매하면 **한 단계 높게** 잡고 시작한 뒤, 영향이 작다고 확인되면 강등한다.
- 데이터 손상/유출 가능성이 있으면 영향 규모와 무관하게 **SEV1**로 시작한다.
- 등급은 대응 중 변동될 수 있으며, 변경 시각을 타임라인에 기록한다.

## 2. 역할 (Roles)

| 역할 | 책임 |
| --- | --- |
| **Incident Commander (IC)** | 대응 총괄. 의사결정(롤백 여부 등), 역할 배정, 진행 조율. 직접 디버깅하지 않는다. |
| **Operations / Responder** | 실제 완화·복구 작업 수행(재시작, 롤백, 스케일 등). [runbook](./runbook.md) 절차 사용. |
| **Communications (Comms)** | 내부/이해관계자 공지, 상태 업데이트 주기 발신. |
| **Scribe** | 타임라인 기록(감지 시각, 조치, 결과). 포스트모템 입력 확보. |

소규모 팀에서는 한 사람이 여러 역할을 겸할 수 있으나, **IC는 반드시 한 명**으로 명확히 지정한다.

## 3. 대응 흐름 (감지 → 완화 → 복구 → 공유)

```text
 ┌─────────┐   ┌─────────┐   ┌─────────┐   ┌─────────┐   ┌─────────┐
 │ DETECT  │──▶│ TRIAGE  │──▶│MITIGATE │──▶│ RECOVER │──▶│ REVIEW  │
 │ 감지    │   │ 분류    │   │ 완화    │   │ 복구    │   │ 공유    │
 └─────────┘   └─────────┘   └─────────┘   └─────────┘   └─────────┘
  알림/제보     SEV 산정       영향 차단      근본 해결     포스트모템
  지표 이상     IC 지정        (롤백/우회)    재발 확인     재발방지
```

### 3.1 DETECT (감지)

- 알림(임계값 초과), 사용자 제보, 대시보드 이상으로 감지한다.
- 알림 임계값은 [observability](../architecture/observability.md)의 골든 시그널 표를 따른다.

### 3.2 TRIAGE (분류)

- 영향 범위 파악 → SEV 등급 산정(§1) → **IC 지정**.
- SEV1/2는 전용 대응 채널을 열고 Scribe가 타임라인 기록을 시작한다.

### 3.3 MITIGATE (완화) — 최우선

사용자 영향을 먼저 멈춘다. 자주 쓰는 완화 수단:

| 수단 | 참고 |
| --- | --- |
| 직전 안정 버전으로 롤백 | [rollback-guide](./rollback-guide.md) |
| 인스턴스 스케일 아웃(포화 시) | [runbook §2.6](./runbook.md#26-스케일-조정) |
| 문제 인스턴스 트래픽 제외 | [runbook §2.7](./runbook.md#27-인스턴스-트래픽-제외) |
| 기능 플래그 off / 비핵심 기능 차단 | (기능 플래그 운영 시) |
| 캐시 무효화 | [runbook §2.5](./runbook.md#25-캐시-비우기) |

> 완화는 "근본 원인을 몰라도" 할 수 있다. 원인 분석은 완화 후에 진행한다.

### 3.4 RECOVER (복구)

- 근본 원인을 해결(hotfix 또는 정식 수정)하고 정상 상태를 확인한다.
- 핵심 지표가 사고 이전 수준으로 복귀했는지 확인한다.
- 스모크 테스트로 주요 시나리오 정상 동작을 검증한다.

### 3.5 REVIEW (공유)

- 사고 종료 선언 후 포스트모템(§5)을 작성한다.
- SEV1/2는 포스트모템 작성을 **필수**로 한다.

## 4. 커뮤니케이션

| 등급 | 내부 알림 | 업데이트 주기(예시) | 종료 공지 |
| --- | --- | --- | --- |
| SEV1 | 즉시 전체 + 이해관계자 | 30분마다 | 필수 |
| SEV2 | 담당 + 온콜 | 1시간마다 | 필수 |
| SEV3 | 담당 채널 | 진행/종료 시 | 권장 |

상태 업데이트 메시지 예시:

```text
[SEV2 / 진행 중] 결제 조회 API 에러율 상승
- 영향: 결제 내역 조회 일부 실패(약 X% 요청)
- 현재 조치: 직전 버전으로 롤백 진행 중 (rollback-guide)
- 다음 업데이트: 1시간 내 / IC: <이름>
```

> 메시지에 실제 시크릿/개인정보/실명 연락처를 노출하지 않는다. 채널/주소는 가짜 예시(example.com)로만 문서화한다.

## 5. 포스트모템 템플릿

> 비난 없는(blameless) 회고를 지향한다. 사람이 아니라 **시스템·프로세스**를 고친다.

```md
# Postmortem: <짧은 제목>

- 심각도: SEV<n>
- 발생 일시 / 감지 일시 / 복구 일시: <YYYY-MM-DD HH:MM> (TZ)
- 지속 시간: <분/시간>
- IC: <이름>   기록: <이름>
- 영향: <영향받은 사용자/기능/규모>

## 요약
무슨 일이 있었는지 2~3문장.

## 타임라인
| 시각 | 이벤트 | 조치 |
| --- | --- | --- |
| HH:MM | 알림 발생(에러율 임계 초과) | TRIAGE 시작, IC 지정 |
| HH:MM | 원인 추정: <배포 X 변경> | 롤백 결정 |
| HH:MM | 롤백 완료 | 지표 정상화 확인 |
| HH:MM | 사고 종료 선언 | - |

## 근본 원인 (Root Cause)
왜 발생했는가. (5 Whys 등으로 표면 원인 너머까지)

## 감지/대응에서 잘된 점 / 아쉬운 점
- 잘된 점:
- 아쉬운 점:

## 재발 방지 액션
| 액션 | 담당 | 기한 | 상태 |
| --- | --- | --- | --- |
| 알림 임계값 조정 | <담당> | <날짜> | 예정 |
| deployment-check 항목 보강 | <담당> | <날짜> | 예정 |
| 모니터링 지표 추가 | <담당> | <날짜> | 예정 |
```

## 6. 체크리스트

대응 중:

- [ ] SEV 등급 산정 및 IC 지정
- [ ] 완화(롤백/우회)로 사용자 영향 우선 차단
- [ ] 타임라인 기록 시작(Scribe)
- [ ] 정해진 주기로 상태 공지(§4)

종료 후:

- [ ] 지표 정상 복귀 확인([observability](../architecture/observability.md))
- [ ] 사고 종료 공지
- [ ] (SEV1/2) 포스트모템 작성(§5)
- [ ] 재발 방지 액션 등록 및 추적
